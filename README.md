# Prospective Wine author run with raw strace

This is a public candidate for a GitHub-hosted Ubuntu experiment. It downloads and verifies the exact public author-code archive and UCI Wine input, builds a Docker image, and runs the unchanged author learning/pruning code through a compatibility caller for 25 fixed splits. The container has no network and a read-only root filesystem. Raw `strace` captures selected file, read, process-start, and connection syscalls.

The first job retains success or failure receipts, including exact copies of the downloaded author ZIP and Wine raw data. A second VM verifies the source snapshot, the expected GitHub repository/commit/run identity supplied by that VM, the retained input bytes against frozen lengths and SHA-256 values, the returned 25-row CSV and arithmetic, and a same-PID successful author `execve` preceding positive `openat`/`read` events for Wine. An offline caller must obtain those expected identity values from an independently trusted source, such as the GitHub run and artifact attestation; passing values copied from the tar would not establish identity. The repository does not include the author archive, UCI data, API keys, human labels, or historical execution evidence; a future run artifact would include the two public input files.

The v04 verifier omitted that `execve` binding. An offline, explicitly synthetic passing fixture still passed v04 after its author `execve` line was removed. The [first real failed run](https://github.com/SHiJiE1115/newproj/actions/runs/36583899749) left trace files owner-writable by the same UID as the traced author process, so v04 also lacked an independent trace-writer boundary. This permission finding does not claim that the author changed a trace.

This v09 development candidate retains the v05 isolation design: root `strace` observes a `setpriv` launcher that drops to UID/GID 65534 before executing the author caller. The trace files are created in a root-owned private directory under a sticky result directory. The author caller checks its IDs and effective capabilities, tests that it cannot write to or rename the observer directory, and checks that it inherited no observer file descriptor. After the traced process exits, the observer makes the trace directory readable for the GitHub runner to package it. The second VM checks the frozen runner, reported runtime permissions, tar trace ownership, canary results, and same-PID event order. The v07 hosted run failed before the author process started: strace 6.8 resolves `--user` by account name and rejected `65534:65534`. [That failed run](https://github.com/SHiJiE1115/newproj/actions/runs/38135533716) is retained. v08 uses root strace to trace `setpriv --reuid=65534 --regid=65534 --clear-groups --inh-caps=-all --ambient-caps=-all`, which then executes the unchanged author caller in the same PID. The empty supplementary-group and zero-effective-capability checks remain unchanged. The v08 author computation and isolation checks passed, but the workflow failed its read-path observation gate; no v08 release or attestation is claimed.

v06 rejected nonportable tar member names before extraction. The v05 POSIX-only name check could accept a member such as `..\\escape.txt`; a Windows postrun verifier would then resolve it outside its temporary extraction directory. v07 additionally rejects two names that differ only by ASCII case, because Windows otherwise writes both to the same physical file while the parser records two separate tar metadata entries. The fixed verifier rejects both aliasing patterns, drive/alternate-stream colons, reserved Windows device names, noncanonical path segments, and resolved paths outside the extraction root. These are verifier safety repairs, not new scientific execution evidence.

The target is Leboeuf et al., NeurIPS 2020, Table 1 Wine/Ours, reported as `0.904 ± 0.046`. The Wine data were used to choose the prior exponent in the paper, so this is not an independent blind test of that number. A successful workflow would add a **new prospective execution observation** tied to a GitHub workflow identity. It would not prove a complete byte-level readset, authenticate the original 2020 run, establish scientific ground truth, or show an advantage over a same-information fixed baseline.

The retained dataset is [Aeberhard and Forina, *Wine* (1992), UCI Machine Learning Repository, DOI:10.24432/C5PC7J](https://archive.ics.uci.edu/dataset/109/wine), licensed there under CC BY 4.0. The author ZIP includes its own MIT license file.

The workflow is manual (`workflow_dispatch`). [The first hosted run](https://github.com/SHiJiE1115/newproj/actions/runs/36583899749) **failed**: the author code produced a 25-row CSV and selected syscall trace, then tried to write its summary to read-only `/probe/out` instead of the writable `/out` mount. The second job was skipped; this is not a passing or attested experiment. Revision v02 fixed that path but was not run. Revision v03 additionally checks the receipt's GitHub identity against values supplied by the second VM; it also has **not run**. Revision v04 retains the downloaded input bytes and has **not run**. Revision v05 added trace separation and the same-PID gate but was not run. v06 added portable tar extraction and was not run. v07 closed a Windows case-alias gap but its hosted run failed on the strace username parameter. v08 repaired startup and completed all 25 draws, reproducing 0.904 and population SD 0.04606811918168868. Its workflow still failed because `strace -yy` returned bare descriptor numbers for read syscalls, so no verified release was obtained. v09 adds DAC_READ_SEARCH only to the root observer capability contract, to permit traversal of the other-UID `/proc/PID/fd` directory. Both acceptance implementations require that exact capability list. Author effective capabilities must still be zero, and the positive read-path and same-PID sequence checks remain unchanged. This hypothesis requires a fresh hosted run; this source snapshot claims no v09 success. The runner's source-byte freeze is in `experiment/FREEZE.json`; the GitHub workflow will fail closed if a frozen file changes. The verified author ZIP and UCI data are fetched at run time from the pinned URLs in `experiment/PROTOCOL.json`. Ubuntu base-image digest is pinned; apt package versions are observed and recorded during the build/run, not byte-pinned in this candidate.

Under continuing project authorization, the manual workflow remains **Actions → RRNC prospective Wine author strace → Run workflow**. The job is capped at 25 minutes; the container author step at 300 seconds. Download and preserve the artifact and attestation because Actions artifacts expire. A failure is retained as a failed protocol run and must not be called a successful trace. The original P1 release gate and local reserve set are unchanged.

## Runtime repair references

The [strace 6.8 source](https://github.com/strace/strace/blob/v6.8/src/strace.c) uses `getpwnam` and `initgroups` for `--user`. The [util-linux setpriv manual](https://github.com/util-linux/util-linux/blob/v2.39.3/sys-utils/setpriv.1.adoc) documents numeric UID/GID selection and explicit supplementary-group clearing. This is an execution compatibility repair, not a scientific method change.

The [v08 failed run](https://github.com/SHiJiE1115/newproj/actions/runs/38136079298) and its raw receipt are retained. Linux defines the [proc FD directory](https://github.com/torvalds/linux/blob/v6.8/fs/proc/fd.c) and checks [directory access permissions](https://github.com/torvalds/linux/blob/v6.8/fs/namei.c); the observer needs access to the descriptor links in addition to ptrace permission. v09 adds no write-bypass capability and does not grant capabilities to the author program.
